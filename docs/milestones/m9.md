# M9 — measured quality and user feedback

Status: recovery messages/actions, minimal feedback and a synthetic worker evaluation
runner with optional Braintrust upload are implemented as candidates. Braintrust account
upload verification and the private pilot remain pending. M1–M8 live and hosted acceptance
remains required independently of this milestone. See [implementation and checks](m9-feedback.md).

The [evaluation guide](../../evals/README.md) covers the 32-case corpus, paid-call budgets,
model comparisons and optional AI judge. See [initial results](m9-evals-verification.md).

The goal is to detect regressions and learn why users cannot finish a documentation task.
Reuse the existing evaluation, telemetry, admission and browser-test infrastructure.

## 1. Reproducible task evaluation

Create a versioned corpus of at least 20 scenarios covering supported documentation
questions, missing answers, source relevance, corrections, interruptions, worker overload,
provider recovery and language/translate preferences. Each case declares its expected behavior
and whether it needs an offline fixture, browser simulation or a real provider/listener.
Include expected document/source identifiers where applicable rather than matching exact
generated wording. Missing evidence must remain untested, never count as a pass.

Write a machine-readable report with commit, dataset version, execution mode, test counts,
failures and timing definitions. Real runs also record model/provider configuration without
credentials. Compare reports from the same mode and configuration; synthetic orchestration
timings must never be presented as acoustic response latency. Keep paid evaluations explicit
and bounded by a configured call budget. Offline regression checks belong in CI.

Acceptance: all offline cases pass, a deliberately wrong citation or stale result is detected,
and the report identifies skipped live cases. Human listening results use a documented rubric
for intelligibility, language adherence and interruption handling. Establish a baseline before
setting latency or model-quality release thresholds; do not invent thresholds from fake runs.

## 2. Clear states and recovery actions

Use existing session and delegation state to show connecting, listening, working, speaking,
worker busy, reconnecting and ended states. When a state cannot be observed reliably, show
only the known state. Offer a clear manual action after overload or failed recovery; never
silently resubmit a task or resurrect a closed session. Preserve keyboard access, readable
captions and restrained live-region announcements.

Acceptance: browser scenarios cover overload, recovery failure, interruption and close.
Each has a visible explanation and an appropriate action; one user action cannot create
duplicate work. Verify the controls manually with a keyboard and a screen reader.

## 3. Minimal diagnostic feedback

Add an explicit feedback action for wrong answer, unhelpful source, audio problem or other
failure. The initial version uses categories only, without free text or transcript upload.
Associate feedback with an opaque diagnostic ID and a bounded snapshot of known state,
application version and provider kind. Do not store audio, transcript, task text, invitation
tokens, session keys or credentials. Tell the user which fields will be submitted.

Use authenticated submission with identity isolation, request-size and per-user rate limits.
Define an allowlisted schema, a bounded durable store, a seven-day retention period and an
expiry cleanup operation. Any operator export must require separate operator authorization
and contain only the same allowlisted fields. Expired records must also disappear from exports.

Acceptance: tests cover unauthorized access, cross-user isolation, duplicate submission,
rate limits, retention and exclusion of sensitive fields. A small invited pilot produces
actionable feedback that can be linked to an evaluation case without recording conversations.

## Delivery order and completion

Implement the evaluation corpus/report first, then interface states, then feedback collection.
Keep each increment reviewable and tested. Run a private pilot only after the existing HTTPS,
invitation, spending and live-call checks pass. Triage its findings and fix blocking defects.
M9 is complete when the regression suite, recovery UX, bounded feedback path and pilot evidence
are present. More providers, cross-host availability and automatic external actions are outside
this milestone's scope.
